Feasibility analysis · 2026-11-21

A Godot app on Android as the central for the rcbench nodes

The app replaces the panel as the Bluetooth LE (Low Energy, BLE) central for the power node, the balance node and the planned servo node. It can hold links to several nodes at once. For the servo node the phone may ARM and drive outputs.

FeasibleThe app itselfGodot renders the screens and decodes packets of 20 to 102 bytes. Nothing in the node protocol exceeds what an Android phone's BLE link carries.
Needs own pluginBluetooth accessGodot has no BLE API. No published Godot plugin is both verified on Android hardware and able to set the MTU and the connection interval.
Not measurable yetSTOP latency and timingNo node has run on hardware and the servo node's protocol is a draft. Every timing figure for a phone is unmeasured.

Bluetooth access: what exists and what is tested

The node protocol needs five things from the central: a scan with manufacturer data, notifications, write without response, an ATT MTU (attribute protocol maximum transmission unit) of 105 or more for the servo node, and a connection interval short enough for a keep-alive every 50ms.

Finding. Bluetooth access is available, and both layers under it are established: Android's API and Godot's plugin mechanism. A ready-made, device-tested Godot plugin that covers the node protocol does not exist. The app needs its own Kotlin plugin of about 10 methods and 8 signals. GodotAndroidBle is a working reference for the plugin structure and the runtime permissions.

Permissions: BLUETOOTH_SCAN and BLUETOOTH_CONNECT from Android 12 (API 31); ACCESS_FINE_LOCATION on Android 6 to 11. The Android emulator has no BLE radio, so every test needs a real phone.

Limits and open points

  • One central per node. Each node accepts 1 connection (CONFIG_BT_NIMBLE_MAX_CONNECTIONS=1). A node linked to the phone is not available to the panel, and the reverse.
  • Several nodes per phone. Android's stack has commonly allowed 7 concurrent BLE connections; the figure is not checked for a specific phone, and a watch or earbuds on BLE count against it. The panel is configured for 5. Each added link takes radio time from the servo node's 50ms keep-alive; the number of links a phone holds before a gap approaches 300ms is not measured.
  • No pairing, no encryption. Any central in range can ARM the servo node and switch a 3,000mA rail. A tap on the node's own touch screen to accept a new central is the smallest guard; the plan does not contain it.
  • Keep-alive source. The keep-alive stops when Godot's main loop stops. A plugin thread that keeps sending behind a frozen screen holds outputs on without a working STOP.
  • Safety logic. The stop latch and the 2s hold exist as host-tested C in shared/. Compiled into a GDExtension for ARM64 they stay one implementation. Whether those files build without the panel's other sources is not checked.
  • Programming and DShot. Servo and ESC (electronic speed controller) programming needs the tunnelled link frames and the panel's programmer logic. The mock-ups leave it out.
  • Hardware. The sensor node boards are ordered and not delivered. The servo node has no firmware and no carrier board. An app written now runs against a simulated node only.
  • Contract wording. "The node does not drive outputs without a linked panel" needs "panel or phone" in the plan and its decisions file. Neither file was changed.

Order of work, if it goes ahead

  1. Kotlin plugin: scan, connect, MTU 247, high priority, subscribe, write without response. Test against the power node firmware on one ESP32-C6 board.
  2. Measure on one phone: connection interval, notification gaps over 10 minutes, and the time from touch to a pin edge on the node.
  3. Power and balance screens. These carry no safety duty.
  4. Servo screens after the plan's throughput measurement fixes the packets, and after the access guard is decided.

Effort in days is not estimated.
